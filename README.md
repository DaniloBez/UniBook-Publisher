# UniBook Publisher

Модульна платформа для автоматизації видавничих процесів: супровід повного життєвого циклу рукописів від первинного подання автором до по-главної редактури, рецензування, дизайну обкладинок, фінансового контрактування та нарахування роялті.

## 2. Архітектура системи (Spring Modulith)

Проєкт спроєктовано за парадигмою модульного моноліту на базі Spring Modulith. Домени інкапсульовані та взаємодіють між собою через асинхронні транзакційні доменні події з використанням `@ApplicationModuleListener`, що гарантує надійність доставлення, ізоляцію збоїв та усуває пряму циклічну зв'язаність між модулями.

```
src/main/java/com/unibook/publisher/
├── production/        # Життєвий цикл рукописів, розділи, версіонування, дизайн, рецензування, diff-порівняння
├── finance/           # Видавничі контракти, стратегії роялті, нарахування виплат, фіксація продажів
├── identity/          # Користувачі, ролі, профілі, автентифікація (JWT) та авторизація
├── communication/     # Сповіщення користувачів, асинхронна реакція на події життєвого циклу
├── storage/           # Абстракція файлового сховища (S3/MinIO та Local), presigned URL, збереження файлів
└── common/            # Спільне доменне ядро: події, енуми, безпека, винятки, логування, OpenAPI
```

### 2.1. Опис модулів

- **production**: Відповідає за процес підготовки книги до друку: приймання рукописів, редакторську модерацію головним редактором, розбиття на розділи, завантаження ревізій із текстовим контентом, построкове diff-порівняння версій, коментування фрагментів тексту з перевіркою цитат, пропозиції та автозаміну правок через треди, ведення довідника літературних жанрів, підготовку варіантів обкладинок та фіналізацію перед публікацією.
- **finance**: Керує договірними відносинами з авторами: формування контрактів при схваленні рукопису, зміна ставок авторського роялті й розміру авансу бухгалтером, протоколювання фінансового аудиту, симуляція та розрахунок винагороди на основі гнучких стратегій нарахування роялті (фіксована ставка, прогресивна шкала від обсягу, покриття авансу), активація контракту при виході книги в друк.
- **identity**: Забезпечує управління обліковими записами, профілями авторів та співробітників, автентифікацію на основі JWT-токенів (Access + Refresh) із використанням BCrypt-хешування паролів та розподіл прав доступу на базі ролей (`AUTHOR`, `EDITOR`, `CHIEF_EDITOR`, `DESIGNER`, `ACCOUNTANT`, `ADMIN`).
- **communication**: Централізований сервіс доставлення сповіщень. Асинхронно слухає події інших модулів через `@ApplicationModuleListener` та формує сповіщення користувачам щодо зміни статусів рукописів, призначень у команду, нових коментарів, ревізій чи підтвердження умов контрактів.
- **storage**: Модуль абстракції файлового сховища на базі інтерфейсу `FileStorageService`. Забезпечує збереження, завантаження, видалення файлів і формування presigned URL. Підтримує легке перемикання між хмарним S3-сумісним сховищем MinIO (`S3FileStorageService`) та локальним дисковим сховищем (`LocalFileStorageService`) через Spring Boot автоконфігурацію `FileStorageAutoConfiguration`.
- **common**: Спільний фундаментальний модуль, який містить:
  - Доменні події (`common.event`): незмінні записи (records), що передаються між модулями через шину подій Spring.
  - Загальні переліки (`common.enums`): статуси контрактів, типи тредів (`ThreadType`), стратегії роялті, системні ролі (`UserRole`).
  - Доменні винятки (`common.exception`): типізована ієрархія помилок на чолі з абстрактним `DomainException`.
  - Підсистему безпеки (`common.security`): конфігурація Spring Security, фільтр валідації JWT (`JwtAuthenticationFilter`), генератор токенів (`JwtService`), обробники помилок 401/403 з ProblemDetail.
  - Підсистему логування та трасування (`common.logging`): уніфікований інтерфейс `AppLogger` з реалізацією `Slf4jAppLogger`, контекстне трасування запитів `RequestLoggingFilter` (`X-Request-Id`), конвертер захисту конфіденційних даних `MaskingMessageConverter` (`LogMasker`) та конфігурація асинхронного запису `logback-spring.xml`.
  - Документацію API (`common.openapi`): конфігурація специфікації OpenAPI 3.0 та інтерактивного Swagger UI (`OpenApiConfiguration`).
  - Централізований обробник помилок (`GlobalExceptionHandler`), що трансформує винятки у стандартні HTTP-відповіді RFC 9457 (`ProblemDetail`).

## 3. Формальна модель переходів станів

Переходи між станами доменних сутностей строго формалізовані та інкапсульовані в енумах через методи `canTransitionTo(next)` та `allowedTransitions()`. Будь-яка спроба виконати недозволений перехід блокується на рівні доменної моделі та викликає виняток `InvalidStateTransitionException`.

### 3.1. Життєвий цикл рукопису (ManuscriptStatus)

Стани рукопису відображають послідовні етапи підготовки книги:
- `SUBMITTED`: Рукопис надіслано автором; очікує первинної редакційної оцінки.
- `POSTPONED`: Розгляд відкладено редактором; рукопис повернено автору на доопрацювання з обов'язковим коментарем.
- `IN_PROGRESS`: Рукопис схвалено редактором; ведеться по-главна редактура, завантаження ревізій та обговорення правок.
- `TEXT_APPROVED`: Роботу редактора над текстом успішно завершено (усі зауваження та треди закрито).
- `IN_DESIGN`: Текст передано дизайнеру; триває розробка та затвердження обкладинки.
- `PUBLISHED`: Книгу опубліковано у видавництві (наявна затверджена обкладинка). Фінальний успішний стан.
- `REJECTED`: Рукопис відхилено редактором із зазначенням причини. Термінальний стан.

#### Матриця переходів станів рукопису

| Поточний стан     | SUBMITTED | POSTPONED | IN_PROGRESS | TEXT_APPROVED | IN_DESIGN | PUBLISHED | REJECTED  |
|:------------------|:---------:|:---------:|:-----------:|:-------------:|:---------:|:---------:|:---------:|
| **SUBMITTED**     |     -     | ДОЗВОЛЕНО |  ДОЗВОЛЕНО  |       -       |     -     |     -     | ДОЗВОЛЕНО |
| **POSTPONED**     |     -     |     -     |  ДОЗВОЛЕНО  |       -       |     -     |     -     | ДОЗВОЛЕНО |
| **IN_PROGRESS**   |     -     |     -     |      -      |   ДОЗВОЛЕНО   |     -     |     -     |     -     |
| **TEXT_APPROVED** |     -     |     -     |      -      |       -       | ДОЗВОЛЕНО |     -     |     -     |
| **IN_DESIGN**     |     -     |     -     |      -      |       -       |     -     | ДОЗВОЛЕНО |     -     |
| **PUBLISHED**     |     -     |     -     |      -      |       -       |     -     |     -     |     -     |
| **REJECTED**      |     -     |     -     |      -      |       -       |     -     |     -     |     -     |

#### Списки дозволених переходів:
- `SUBMITTED` ➔ `POSTPONED`, `IN_PROGRESS`, `REJECTED`
- `POSTPONED` ➔ `IN_PROGRESS`, `REJECTED`
- `IN_PROGRESS` ➔ `TEXT_APPROVED`
- `TEXT_APPROVED` ➔ `IN_DESIGN`
- `IN_DESIGN` ➔ `PUBLISHED`
- `PUBLISHED` ➔ переходи відсутні (фінальний стан)
- `REJECTED` ➔ переходи відсутні (термінальний стан)

---

### 3.2. Життєвий цикл видавничого контракту (ContractStatus)

- `DRAFT`: Проєкт контракту створено; умови узгоджуються з автором.
- `ACTIVE`: Контракт підтверджено; діє офіційна ставка роялті, дозволено фіксацію продажів та виплати.
- `TERMINATED`: Договірні відносини розірвано або термін дії вичерпано. Термінальний стан.

#### Матриця переходів станів контракту

| Поточний стан  | DRAFT |  ACTIVE   | TERMINATED |
|:---------------|:-----:|:---------:|:----------:|
| **DRAFT**      |   -   | ДОЗВОЛЕНО | ДОЗВОЛЕНО  |
| **ACTIVE**     |   -   |     -     | ДОЗВОЛЕНО  |
| **TERMINATED** |   -   |     -     |     -      |

#### Списки дозволених переходів:
- `DRAFT` ➔ `ACTIVE`, `TERMINATED`
- `ACTIVE` ➔ `TERMINATED`
- `TERMINATED` ➔ переходи відсутні

---

### 3.3. Життєвий цикл обговорень і коментарів (ThreadStatus)

- `OPEN`: Тред активний; триває обговорення фрагмента тексту, обкладинки чи загальних питань.
- `RESOLVED`: Зауваження враховано, питання узгоджено.

#### Матриця переходів станів обговорення

| Поточний стан |   OPEN    | RESOLVED  |
|:--------------|:---------:|:---------:|
| **OPEN**      |     -     | ДОЗВОЛЕНО |
| **RESOLVED**  | ДОЗВОЛЕНО |     -     |

- Перехід `OPEN` ➔ `RESOLVED`: закриття обговорення після внесення правок.
- Перехід `RESOLVED` ➔ `OPEN`: повторне відкриття треду у разі виникнення нових зауважень.

---

### 3.4. Статуси пропозицій заміни тексту (SuggestionStatus)

- `PENDING`: Редактор запропонував альтернативний варіант фрагмента; очікує рішення автора.
- `ACCEPTED`: Пропозицію прийнято; запропонований текст автоматично застосовується до розділу.
- `REJECTED`: Пропозицію відхилено; оригінальний текст розділу залишається без змін.

#### Матриця переходів станів пропозиції

| Поточний стан | PENDING | ACCEPTED  | REJECTED  |
|:--------------|:-------:|:---------:|:---------:|
| **PENDING**   |    -    | ДОЗВОЛЕНО | ДОЗВОЛЕНО |
| **ACCEPTED**  |    -    |     -     |     -     |
| **REJECTED**  |    -    |     -     |     -     |

- `PENDING` ➔ `ACCEPTED`, `REJECTED`
- `ACCEPTED`, `REJECTED` ➔ термінальні стани

## 4. Опис бізнес-правил платформи

### 4.1. Модуль Production

1. **Правило валідації переходів станів**: Будь-яка зміна статусу рукопису повинна відповідати методу `ManuscriptStatus.canTransitionTo()`. При спробі не валідного переходу генерується `InvalidStateTransitionException` (HTTP 422) із повним контекстом допустимих станів.
2. **Правило модерації та обов'язкового обґрунтування**: 
   - Модераційні рішення щодо рукопису приймаються виключно головним редактором (`UserRole.CHIEF_EDITOR`) на основі перевірки контексту безпеки Spring Security (`@AuthenticationPrincipal AuthenticatedUser`). При спробі виконати дію користувачем з іншою роллю викидається `ForbiddenActionException` (HTTP 403).
   - Схвалення рукопису (`approveManuscript`) переводить твір зі статусу `SUBMITTED` або `POSTPONED` у статус `IN_PROGRESS`, обов'язково призначає відповідального редактора, публікує подію `ManuscriptApprovedEvent` (яка автоматично ініціює створення контракту у модулі `finance`) та призначення персоналу `WorkerAssignedEvent`.
   - Відхилення рукопису (`rejectManuscript`) вимагає непорожньої причини (`reason`). Переводить рукопис у статус `REJECTED` та генерує `ManuscriptRejectedEvent`.
   - Відкладення рукопису (`postponeManuscript`) вимагає обов'язкового коментаря редактора (`comment`). Переводить рукопис у статус `POSTPONED` та генерує `ManuscriptPostponedEvent`.
3. **Правило фіналізації тексту**: Завершення редакторської роботи над текстом (`finalizeText`) дозволено виключно призначеному редактору рукопису та за умови, що всі треди обговорень для всіх розділів мають статус `RESOLVED`. Якщо існує хоча б один відкритий тред (`ThreadStatus.OPEN`) або нерозглянута пропозиція правки, дія блокується викиданням `UnresolvedThreadsException` (HTTP 422). Успішна фіналізація переводить рукопис у `TEXT_APPROVED` та публікує `TextFinalizedEvent`.
4. **Правило обов'язкової наявності обкладинки для публікації**: Переведення книги зі статусу `IN_DESIGN` у `PUBLISHED` (`publishBook`) виконується головним редактором і дозволено тільки у випадку, коли в системі зареєстровано хоча б одну версію обкладинки для цього рукопису. Якщо обкладинка відсутня, викидається `MissingCoverException` (HTTP 422). Публікація генерує `ManuscriptPublishedEvent`, що автоматично активує договір у модулі `finance`.
5. **Правило унікальності активної обкладинки**: Одночасно затвердженою (`isApproved == true`) для рукопису може бути лише одна версія обкладинки. Затвердження нової версії автоматично деактивує статус попередньої.
6. **Правило валідації цитування тексту**: Для тредів обговорень, що створюються з прив'язкою до ревізії розділу (`targetRevisionId`), здійснюється сувора перевірка:
   - Текст цільової ревізії не може бути порожнім або відсутнім (інакше `EmptyRevisionTextException`, HTTP 422).
   - Символьні позиції повинні задовольняти умовам: `0 <= positionFrom < positionTo <= textContent.length()` (інакше `InvalidQuotePositionException`, HTTP 422).
   - Текст підрядка за вказаними координатами повинен точно збігатися з переданою цитатою `quotedText` (інакше `InvalidQuoteException`, HTTP 422).
7. **Правило операцій над пропозиціями та автоматичної заміни тексту**: Операції прийняття (`acceptSuggestion`) та відхилення (`rejectSuggestion`) правок можуть застосовуватися виключно автором твору та лише до тредів, створених як пропозиції заміни тексту (`isSuggestion == true`) у статусі `PENDING`. При спробі застосувати їх до звичайного обговорення викидається `ThreadNotASuggestionException` (HTTP 422). Прийняття пропозиції автоматично замінює фрагмент тексту ревізії у діапазоні `[positionFrom, positionTo)` на `suggestedText`, зберігає оновлену ревізію та переводить тред у статус `RESOLVED` зі статусом пропозиції `ACCEPTED`.
8. **Правило порівняння ревізій розділу (Diff Engine)**: Платформа підтримує побудову построкової різниці (diff) між будь-якими двома ревізіями розділу (`GET /api/v1/{chapterId}/diff?fromRevisionId=...&toRevisionId=...`). Порівняння повертає структуровану відповідь `DiffResponse`, яка містить перелік рядків із їхнім статусом `DiffStatus` (`EQUAL`, `INSERTED`, `DELETED`) та 1-based номерами у вихідній (`oldLineIndex`) і цільовій (`newLineIndex`) версіях.
9. **Правило унікальності призначення співробітника**: Один і той самий користувач не може бути призначений двічі на одну й ту саму роль (`UserRole`) для одного рукопису. Повторна спроба блокується винятком `StaffAlreadyAssignedException` (HTTP 409).
10. **Правило обов'язкового аудиту дій**: Усі редакторські дії (зміна станів, відкладення, схвалення, фіналізація, призначення персоналу) фіксуються в журналі аудиту `ManuscriptAuditLog` із зазначенням автора дії, ідентифікатора рукопису, типу операції та мітки часу.
11. **Правило довідника літературних жанрів (Genres)**: Назва літературного жанру є строго унікальною без урахування регістру (при дублюванні викидається `DuplicateResourceException`, HTTP 409). Рукопис пов'язується з множиною жанрів (`ManyToMany`) через проміжну таблицю `manuscript_genres`.
12. **Правило валідації файлових завантажень**:
    - **Ревізії розділів**: дозволено завантаження виключно текстових файлів із розширеннями `.txt` та `.md` (MIME-типи `text/plain`, `text/markdown`, `text/x-markdown`, `application/octet-stream`). Інші розширення викликають `InvalidFileTypeException` (HTTP 400).
    - **Обкладинки**: дозволено графічні формати `.jpg`, `.jpeg`, `.png`, `.webp` (MIME-типи `image/jpeg`, `image/png`, `image/webp`). Порожні файли відхиляються з `FileIsEmptyException` (HTTP 400).
    - **Обмеження розміру**: максимальний ліміт на один файл та загальний розмір запиту становить 10 МБ (`spring.servlet.multipart.max-file-size=10MB`).
13. **Правило призначення команди (Team Assignment)**: Головний редактор призначає відповідального редактора на етапі схвалення рукопису (`approveManuscript`) та призначає дизайнера обкладинки при переході рукопису у статус `IN_DESIGN` (`assignDesigner`). Записи зберігаються у таблиці `team_assignments` із каскадним видаленням при видаленні рукопису.

### 4.2. Модуль Finance

1. **Правило активності контракту для фінансових розрахунків**: Операції фіксації продажу книг та нарахування авторської винагороди (роялті) дозволені виключно за наявності контракту у статусі `ContractStatus.ACTIVE`. Спроба нарахувати кошти за неактивним або розірваним контрактом викликає виняток `ContractNotActiveException` (HTTP 422).
2. **Правило процентної ставки роялті**: Ставка авторського роялті повинна бути строго додатною та не перевищувати 100% (`0 < royaltyPercent <= 100`).
3. **Правило стратегій розрахунку роялті (RoyaltyStrategy)**: Розрахунок винагороди автора та симуляція виплат (`simulatePayout`) підтримують вибір алгоритму згідно з патерном Strategy (`RoyaltyStrategyType`):
   - `FLAT_RATE` (Фіксована ставка): роялті розраховується як прямий відсоток від суми продажів: $\text{salesAmount} \times \text{royaltyPercent} / 100$.
   - `TIERED_VOLUME` (Прогресивна шкала): процентна ставка змінюється динамічно залежно від обсягу продажів (до 1 000 грн — 5%, від 1 000 до 5 000 грн — 7%, понад 5 000 грн — 10%).
   - `ADVANCE_RECOUPMENT` (Покриття авансу): нараховане за базовою ставкою роялті спочатку спрямовується на погашення раніше виданого автору авансу (`advancePayment`), і лише залишок понад суму авансу нараховується до виплати ($\max(0, \text{royalty} - \text{advancePayment})$).
   - При спробі використання непідтримуваної або невідомої стратегії генерується виняток `UnsupportedRoyaltyStrategyException` (HTTP 422).
4. **Правило аудиту фінансових параметрів**: Кожне оновлення ставки роялті фіксується у фінансовому журналі аудиту `FinanceAuditLog` із фіксацією попереднього та нового відсотка, авансу та причини коригування і супроводжується публікацією події `ContractRoyaltyUpdatedEvent`.
5. **Правило незворотності розірвання**: Переведення контракту у статус `TERMINATED` є остаточним; відновлення розірваного контракту заборонено.
6. **Правило реактивного життєвого циклу контракту**:
   - При схваленні рукопису редактором (`ManuscriptApprovedEvent`) слухач `ManuscriptEventListener` автоматично створює видавничий договір у стані `DRAFT` із дефолтними фінансовими параметрами.
   - При фінальній публікації книги (`ManuscriptPublishedEvent`) договір автоматично активується (`status = ACTIVE`).
7. **Правило редагування умов контракту бухгалтером**: Зміна процентної ставки та авансу (`updateRoyalty`, `updateContract`) захищена перевіркою `@PreAuthorize("hasRole('ACCOUNTANT')")` і дозволена виключно у статусі `DRAFT`. Будь-яке оновлення умов автоматично анулює попереднє схвалення автора (`authorConfirmedAt = null`).
8. **Правило підтвердження контракту автором**: Підтвердження умов договору (`confirmContract`) доступне лише автору рукопису у стані `DRAFT`. Метод є ідемпотентним і публікує подію `ContractConfirmedEvent`.
9. **Правило видалення контрактів**: Видалення контракту дозволено лише адміністратору (`ADMIN`) і виключно для договорів, які не є активними (`status != ACTIVE`).

### 4.3. Модуль Identity

1. **Правило унікальності адреси електронної пошти**: Реєстрація нового автора (`register`) або створення облікового запису співробітника адміністратором (`createStaff`) з електронною поштою, яка вже зареєстрована в системі (без урахування регістру), заборонена. Викидається виняток `EmailAlreadyExistsException` (HTTP 409).
2. **Правило захищеної автентифікації**: У разі невірного пароля або відсутності користувача з вказаною поштою сервіс повертає уніфікований виняток `InvalidCredentialsException` (HTTP 401) без розкриття інформації про те, яка саме частина облікових даних була невірною.
3. **Правило криптографічного захисту паролів**: Паролі користувачів обов'язково хешуються алгоритмом BCrypt із використанням випадкової солі перед збереженням у базі даних. Збереження паролів у відкритому вигляді суворо заборонено.
4. **Правило розподілу обов'язків (Role-Based Access Control)**:
   - `AUTHOR`: Подання власних рукописів, створення розділів, завантаження ревізій тексту, участь в обговореннях, прийняття або відхилення правок, підтвердження умов контракту, симуляція роялті, редагування власного профілю.
   - `EDITOR`: По-главна редактура закріплених рукописів, завантаження виправлених ревізій, відкриття тредів із цитатами та пропозиціями заміни тексту, затвердження тексту книги (`finalizeText`).
   - `CHIEF_EDITOR`: Головний редактор із виключними правами первинної модерації заявок (схвалення, відхилення, повернення на доопрацювання), призначення редакторів та дизайнерів, фінальної публікації книг, перегляду повного списку користувачів.
   - `DESIGNER`: Завантаження та оновлення версій графічних обкладинок книг у статусі `IN_DESIGN`, обговорення художнього оформлення.
   - `ACCOUNTANT`: Управління договірними відносинами з авторами, перегляд усіх контрактів, зміна ставок роялті та розміру авансу для проєктів у статусі `DRAFT`, симуляція нарахувань виплат за різними моделями.
   - `ADMIN`: Створення та адміністрування облікових записів співробітників (`createStaff`), видалення користувачів і неактивних контрактів, глобальний моніторинг.
5. **Архітектура автентифікації на базі JWT (Stateless Token-based Auth)**:
   - Застосунок працює в безсесійному режимі (`SessionCreationPolicy.STATELESS`).
   - Після успішного входу (`/api/v1/auth/login`) або реєстрації (`/api/v1/auth/register`) клієнт отримує пару токенів:
     - **Access Token**: нетривалий JWT-токен (за замовчуванням 30 хв), що містить ідентифікатор користувача, email та роль (`ROLE_*`). Передається у HTTP-заголовку: `Authorization: Bearer <access_token>`.
     - **Refresh Token**: довгоживучий криптографічний токен (за замовчуванням 7 днів) для безпечної ротації пари токенів через ендпоінт `POST /api/v1/auth/refresh`.
   - Завершення сесії (`POST /api/v1/auth/logout`) завершує роботу клієнта з поточними токенами.
6. **Правило доступу до профілів та переліку користувачів**: Користувач може редагувати лише власні дані профілю (`currentUserId == requestedUserId`), спроба редагування чужого профілю відхиляється `ForbiddenActionException` (HTTP 403). Отримання повного переліку користувачів системи з можливістю фільтрації за роллю дозволено виключно головному редактору (`CHIEF_EDITOR`) та адміністратору (`ADMIN`).

### 4.4. Модуль Communication

1. **Правило авторизації доступу до сповіщень**: Користувач має право переглядати та відмічати як прочитані (`markAsRead`) виключно ті сповіщення, адресатом яких він є (`recipientId == currentUserId`). Спроба змінити статус чужого сповіщення відхиляється винятком `ForbiddenActionException` (HTTP 403).
2. **Правило ідемпотентності прочитання**: Повторне позначення сповіщення, яке вже має статус `isRead == true`, є ідемпотентним і не призводить до помилок.
3. **Правило асинхронного реагування на події**: Модуль комунікації є виключно реактивним і формує сповіщення на підставі доменних подій, опублікованих іншими модулями системи:
   - `ManuscriptSubmittedEvent` ➔ сповіщення автору про успішну подачу та взяття на модерацію.
   - `ManuscriptApprovedEvent` ➔ сповіщення автору про схвалення твору головним редактором.
   - `ManuscriptRejectedEvent` ➔ сповіщення автору з обов'язковою причиною відхилення.
   - `ManuscriptPostponedEvent` ➔ сповіщення автору із зауваженнями редактора.
   - `TextFinalizedEvent` ➔ сповіщення про офіційне завершення редактури тексту книги.
   - `ManuscriptPublishedEvent` ➔ сповіщення автору про успішну публікацію книги.
   - `ContractConfirmedEvent` ➔ сповіщення автору про підтвердження умов видавничого контракту.
   - `ContractRoyaltyUpdatedEvent` ➔ сповіщення про зміну відсоткової ставки роялті.
   - `WorkerAssignedEvent` ➔ сповіщення призначеному фахівцю (редактору/дизайнеру) та автору книги про оновлення складу команди.
   - `CoverVersionAddedEvent` ➔ сповіщення автору про завантаження дизайнером нового варіанту обкладинки.
   - `RevisionAddedEvent` ➔ сповіщення адресату (автору або редактору) про завантаження нової текстової версії розділу.
   - `ThreadOpenedEvent` ➔ сповіщення про відкриття нового обговорення із типом: розділ (`CHAPTER`), обкладинка (`COVER`) або загальне питання (`GENERAL`).
   - `ThreadMessageAddedEvent` ➔ сповіщення адресату про нове повідомлення в гілці обговорення.

### 4.5. Модуль Storage

1. **Абстракція постачальника файлового сховища**: Усі операції взаємодії з файлами (рукописи, ревізії розділів, графічні обкладинки) інкапсульовані в інтерфейсі `FileStorageService`. Інші модулі не залежать від фізичної реалізації сховища.
2. **Підтримка Presigned URLs та локального стрімінгу**:
   - Для S3/MinIO сховища формуються безпечні тимчасові підписані URL (`getPresignedUrl`) для завантаження файлу безпосередньо з об'єктного сховища.
   - Для локальної файлової системи генерується посилання на спеціальний ендпоінт стрімінгу `/api/v1/storage/raw?path=...`.
3. **Автоконфігурація провайдера сховища**: Вибір реалізації здійснюється через налаштування `file-storage.type` (`s3` або `local`):
   - При `type=s3` активується `S3FileStorageService`, що взаємодіє з MinIO/AWS S3 через офіційний клієнт `MinioClient`.
   - При `type=local` активується `LocalFileStorageService`, що зберігає файли у локальній файловій системі (`file-storage.location`, за замовчуванням `./uploads`) із суворою валідацією шляхів проти Directory Traversal атак (`!resolved.startsWith(root)`).

### 4.6. Підсистема аудиту, спостережуваності та захисту логів (Logging & Tracing)

1. **Наскрізне трасування запитів (Correlation ID / X-Request-Id)**: Фільтр `RequestLoggingFilter` автоматично зчитує заголовок `X-Request-Id` із вхідного HTTP-запиту (або генерує новий 8-символьний UUID) та додає його в SLF4J MDC під ключем `requestId`. Кожна відповідь сервера повертає заголовок `X-Request-Id` клієнту.
2. **Протоколювання запитів та тривалості**: Після завершення обробки кожного запиту автоматично логується HTTP метод, URI, статус відповіді та час виконання в мілісекундах:
   - Статуси 2xx/3xx логуються на рівні `INFO`.
   - Клієнтські помилки 4xx логуються на рівні `WARN`.
   - Серверні помилки 5xx логуються на рівні `ERROR`.
3. **Автоматичне маскування конфіденційних даних (LogMasker)**: Конвертер `MaskingMessageConverter` у конфігурації Logback автоматично перехоплює повідомлення та замінює зірочками `****`:
   - Паролі, секретні ключі, токени доступу (включаючи `Bearer ...`), API-ключі.
   - Номери банківських платіжних карток (13-19 цифр) із перевіркою коректності алгоритмом Луна (маскуються всі цифри крім останніх чотирьох: `************1234`).
   - Міжнародні номери банківських рахунків IBAN.
4. **Асинхронне логування та ротація файлів**: Налаштовано `logback-spring.xml` із асинхронним записом (`AsyncAppender`) для мінімізації впливу на I/O-продуктивність та щоденною ротацією лог-файлів (`logs/app.log`, стиснення `.gz`, ліміт 10 МБ на файл, зберігання 14 днів, максимальний сумарний обсяг 500 МБ).

### 4.7. Веб-інтерфейс, шаблонізація Thymeleaf та двошарова безпека

Браузерний інтерфейс побудовано на серверному рендерингу Thymeleaf у поєднанні з двошаровою архітектурою Spring Security та стилізацією на Bootstrap 5.

#### 1. Архітектура двох ланцюгів безпеки
У системі сконфігуровано два ізольованих ланцюги фільтрів безпеки (`SecurityConfig`):
- **`@Order(1) securityFilterChain`**: Обслуговує REST API ендпоінти (`/api/**`, `/swagger-ui/**`, `/v3/api-docs/**`, `/h2-console/**`). Працює в безсесійному режимі (`SessionCreationPolicy.STATELESS`), автентифікація здійснюється через JWT-токени (`JwtAuthenticationFilter`), захист CSRF вимкнено.
- **`@Order(2) webSecurityFilterChain`**: Обслуговує браузерні вебсторінки (`/**`). Працює в сесійному режимі (`HttpSession` / кука `JSESSIONID`), захист CSRF увімкнено за замовчуванням (`Customizer.withDefaults()`), автентифікація здійснюється через кастомну форму входу (`.formLogin().loginPage("/login")`).

#### 2. Рольова переадресація
Після успішної авторизації через форму входу спрацьовує `RoleBasedAuthenticationSuccessHandler`, який аналізує ролі користувача:
- Автори з ролями `AUTHOR`, `EDITOR`, `DESIGNER` ➔ перенаправляються на персональну сторінку `/manuscripts/my`.
- Користувачі з ролями `CHIEF_EDITOR`, `ACCOUNTANT`, `ADMIN` ➔ перенаправляються на загальний реєстр видавництва `/manuscripts`.
- Спроба анонімного доступу до захищених сторінок автоматично перенаправляється на `/login`.

#### 3. Карта сторінок та рольові можливості
- **`GET /login`**: Форма авторизації (поля `email`, `password`, прихований CSRF-токен) з обробкою помилок входу (`?error`) та сповіщенням про успішний вихід (`?logout`).
- **`GET /manuscripts/my`**: Персональний кабінет автора, редактора та дизайнера.
   - Для ролі `AUTHOR`: відображає власні книги та містить кнопку створення нового рукопису (`GET /manuscripts/new`).
   - Для ролей `EDITOR` та `DESIGNER`: відображає закріплені книги з кнопками просування по пайплайну (перехід у стани редагування, дизайн та затвердження).
- **`GET /manuscripts`**: Загальний реєстр усіх рукописів видавництва для менеджменту (`CHIEF_EDITOR`, `ACCOUNTANT`, `ADMIN`).
   - Для ролі `CHIEF_EDITOR`: містить елементи управління модерацією (схвалення, відхилення, повернення на доопрацювання) та просування рукописів за життєвим циклом.
- **`GET /manuscripts/new`**: Форма подання нового рукопису автором із перевіркою полів валідацією JSR-380 (`@NotBlank`, `@Size`).
- **`templates/error/403.html` та `templates/error/404.html`**: Кастомні сторінки помилок у стилі проєкту. Містять контекстну кнопку повернення, яка за допомогою `sec:authorize` динамічно веде на `/manuscripts/my`, `/manuscripts` або `/login` залежно від ролі залогіненого користувача.

#### 4. Версіонування статичних ресурсів
Для запобігання кешуванню застарілих CSS/JS файлів у браузері налаштовано автоматичне додавання MD5-хешу вмісту файлів у їхні URL-адреси:
```properties
spring.web.resources.chain.enabled=true
spring.web.resources.chain.strategy.content.enabled=true
spring.web.resources.chain.strategy.content.paths=/css/**,/js/**
spring.web.resources.chain.cache=true
```
У шаблонах Thymeleaf ресурси підключаються через синтаксис @{~} (наприклад, <link th:href="@{/css/main.css}">), що автоматично трансформує шлях у /css/main-f4e2d3c1.css.

#### 5. Спільні фрагменти Thymeleaf
 - **templates/fragments/common-head.html:** Спільний <head> із підключенням мета-тегів, локального Bootstrap 5, скриптів (bootstrap.bundle.min.js) та кастомних стилів main.css.
 - **templates/fragments/header.html:** Спільна шапка сайту
   - Ліва сторона: Назва бренду UniBook Publisher із динамічним посиланням на відповідну головну сторінку для ролі поточного користувача.
   - Права сторона: Профіль користувача (аватарка, ім'я користувача, бедж із назвою ролі) та HTML-форма виходу POST /logout із прихованим CSRF-токеном.

## 5. Ієрархія доменних винятків та обробка помилок

Усі винятки бізнес-рівня системи організовані в типізовану ієрархію з єдиним базовим абстрактним класом `DomainException` (`extends RuntimeException`). Винятки згруповані за смисловими пакетами відповідно до характеру помилки та транслюються `GlobalExceptionHandler` у відповідні HTTP-статуси згідно зі специфікацією RFC 9457 (`ProblemDetail`).

```
com.unibook.publisher.common.exception/
├── DomainException.java                                # Базовий абстрактний клас
├── GlobalExceptionHandler.java                         # Централізований обробник винятків
│
├── badrequest/                                         # HTTP 400 BAD REQUEST
│   ├── BadRequestException.java                        # Базовий клас некоректного запиту
│   ├── InvalidFileTypeException.java                   # Непідтримуване розширення чи Content-Type файлу
│   └── FileIsEmptyException.java                       # Передано порожній файл
│
├── notfound/                                           # HTTP 404 NOT FOUND
│   ├── ResourceNotFoundException.java                  # Базовий клас для відсутніх ресурсів
│   ├── ManuscriptNotFoundException.java
│   ├── ChapterNotFoundException.java
│   ├── ContractNotFoundException.java
│   ├── UserNotFoundException.java
│   ├── NotificationNotFoundException.java
│   ├── RevisionNotFoundException.java
│   └── FileNotFoundException.java                      # Файл відсутній
│
├── state/                                              # HTTP 422 UNPROCESSABLE ENTITY
│   └── InvalidStateTransitionException.java            # Помилка переходу між станами
│
├── business/                                           # HTTP 422 UNPROCESSABLE ENTITY
```

## 7. Конфігурація та локальний запуск

### 7.1. Змінні оточення

Для зручного локального налаштування параметрів без зміни вихідного коду використовується файл `.env`. У репозиторії надано шаблон `.env.example`, що містить зразок усіх підтримуваних системних змінних.

Для початку роботи скопіюйте шаблон:
```bash
cp .env.example .env
```

> [!NOTE]
> Файл `.env` додано до `.gitignore`, тому локальні налаштування та облікові дані до баз залишаються конфіденційними. Додаток автоматично зчитує змінні з `.env` на старті.

#### Опис груп параметрів:

1. **База даних за замовчуванням (H2 In-Memory)**:
   - `DB_URL`: JDBC URL для вбудованої бази H2 (за замовчуванням `jdbc:h2:mem:unibook_db;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE`).
   - `DB_DRIVER`: драйвер `org.h2.Driver`.
   - `DB_USER` / `DB_PASSWORD`: облікові дані (`sa` / без пароля).
   - `H2_CONSOLE_ENABLED`: активація вебконсолі H2 (`true`).

2. **База даних PostgreSQL (Локальна або спільний сервер команди)**:
   - `DB_HOST`, `DB_PORT`, `DB_NAME`: мережева адреса, порт та назва бази даних (за замовчуванням `localhost:5432/unibook_db`).
   - `DB_USER`, `DB_PASSWORD`: облікові дані користувача PostgreSQL.
   - `DB_URL`: повний JDBC URL (`jdbc:postgresql://${DB_HOST}:${DB_PORT}/${DB_NAME}`).
   - `DB_DRIVER`: драйвер `org.postgresql.Driver`.

3. **JPA та Hibernate**:
   - `JPA_DDL_AUTO`: режим генерації структури БД (`update`, `validate`, `create-drop`).
   - `JPA_SHOW_SQL` / `JPA_FORMAT_SQL`: логування та форматування SQL-запитів у консолі.

4. **Безпека та JWT (JSON Web Tokens)**:
   - `JWT_SECRET`: секретний криптографічний ключ для генерації та підпису підписів HMAC-SHA256 (наприклад: `nY3+e9Pzq4rVb6sK8tZ1yQw2uE5hF0gH3kL9mN0pQ2s=`).
   - `JWT_ACCESS_EXPIRATION`: тривалість життя короткочасного access-токена в мілісекундах (`1800000` = 30 хвилин).
   - `JWT_REFRESH_EXPIRATION`: тривалість життя токена оновлення refresh-токена в мілісекундах (`604800000` = 7 діб).

5. **S3 Сховище (MinIO / Garage / Cloudflare R2)**:
   - `S3_PORT`: зовнішній порт для S3 REST API (за замовчуванням `9000`).
   - `S3_CONSOLE_PORT`: зовнішній порт для вебпанелі MinIO Web Console (за замовчуванням `9001`).
   - `S3_ENDPOINT`: URL точки доступу до S3 API (для локального MinIO: `http://localhost:9000` або порт із `S3_PORT`).
   - `S3_REGION`: регіон сховища (за замовчуванням `us-east-1`).
   - `S3_BUCKET`: назва робочого бакета (за замовчуванням `unibook`).
   - `S3_ACCESS_KEY` / `S3_SECRET_KEY`: облікові дані S3 API / MinIO Root User (за замовчуванням `minioadmin` / `minioadmin`, мінімальна довжина пароля MinIO — 8 символів).

6. **Параметри файлового сховища (`application.properties`)**:
   - `file-storage.enabled`: активація підсистеми роботи з файлами (`true` / `false`).
   - `file-storage.type`: режим зберігання артефактів (`s3` або `local`). При виборі `local` файли зберігаються на сервері без потреби запуску MinIO.
   - `file-storage.location`: шлях до каталогу при локальному режимі (за замовчуванням `./uploads`).
   - `file-storage.server-url`: базовий URL бекенду для генерації direct raw посилань на файли (за замовчуванням `http://localhost:8080`).

### 7.2. Наслідування конфігурацій (Properties & Profiles)

Конфігурація системи побудована за ієрархічним принципом без дублювання налаштувань:
- **`application.properties` (Базовий файл)**: містить спільні налаштування застосунку, Jackson, безпечні дефолти JPA/Hibernate та фолбеки для H2. Усі інші профілі автоматично наслідують ці параметри.
- **`application-postgres.properties` (Профіль Postgres)**: активується прапорцем `--spring.profiles.active=postgres`. Він перевизначає виключно параметри джерела даних (`spring.datasource.*`) під PostgreSQL та вимикає консоль H2, автоматично успадковуючи всі JPA-налаштування з базового файлу.

> [!TIP]
> **Перемикання між H2 та PostgreSQL можна виконати двома зручними шляхами:**
> 1. **Через `.env`**: закоментувати блок H2 та розкоментувати блок PostgreSQL у власному файлі `.env`.
> 2. **Через профіль Spring**: запустити додаток із параметром `--spring.profiles.active=postgres`.

### 7.4. Локальне S3-сховище MinIO (Docker Compose)

Для локального зберігання файлів (рукописів, ревізій та обкладинок) у проєкті передбачено запуск MinIO через Docker Compose. Усі налаштування беруться безпосередньо зі змінних `S3_*` у файлі `.env`.

#### Запуск сховища:
```bash
docker compose up -d
```

#### Що робить `docker-compose.yml`:
1. **`minio`**: запускає контейнер MinIO (`cgr.dev/chainguard/minio:latest`):
   - Порт **`${S3_PORT:-9000}`**: S3 REST API endpoint (відповідає порту в `S3_ENDPOINT`). Якщо стандартний порт `9000` зайнятий іншою службою, його можна змінити в `.env` через `S3_PORT` (і відповідно оновити `S3_ENDPOINT`).
   - Порт **`${S3_CONSOLE_PORT:-9001}`**: Вебконсоль керування (MinIO Web Console). За потреби також змінюється через `S3_CONSOLE_PORT`.
   - Користувач та пароль автоматично призначаються з `S3_ACCESS_KEY` та `S3_SECRET_KEY`.
   - Регіон береться з `S3_REGION`.
   - Дані зберігаються у Docker volume `minio_data`.
2. **`minio-init`**: допоміжний контейнер (`cgr.dev/chainguard/minio-client:latest-dev`), який очікує готовності MinIO та автоматично створює робочий бакет із назвою `S3_BUCKET` (за замовчуванням `unibook`), тому вручну створювати бакет не потрібно.

#### Доступ до вебпанелі MinIO:
- **URL**: [http://localhost:9001](http://localhost:9001) (або порт із `S3_CONSOLE_PORT`)
- **Username**: значення `S3_ACCESS_KEY` (за замовчуванням `minioadmin`)
- **Password**: значення `S3_SECRET_KEY` (за замовчуванням `minioadmin`)

#### Зупинка сховища:
```bash
docker compose down
```

```bash
git clone https://github.com/DaniloBez/UniBook-Publisher.git
```

- **Консоль керування базою даних H2**: `http://localhost:8080/h2-console`
  - JDBC URL: `jdbc:h2:mem:unibook_db`
  - Користувач: `sa`
  - Пароль: *(порожній)*

#### Автентифікація в Swagger UI / Postman / curl:
1. Надішліть `POST /api/v1/auth/login` із логіном (наприклад, `chief.editor@unibook-demo.local`) та паролем `SuperSecretPassword123!`.

### 7.6. Аналіз якості коду та тестового покриття (SonarCloud & JaCoCo)

Для забезпечення високої надійності, безпеки та чистоти коду в проєкті інтегровано зв'язку **JaCoCo + SonarCloud**.

#### 1. Як це працює
- **JaCoCo**: під час запуску тестів збирає статистику виконання рядків і гілок коду та генерує XML-звіт (`build/reports/jacoco/test/jacocoTestReport.xml`) і локальний HTML-звіт (`build/reports/jacoco/test/html/index.html`).
- **SonarCloud**: отримує вихідний код і JaCoCo XML-звіт, аналізує вразливості, баги, code smells та відображає підсумковий відсоток покриття на Quality Gate дашборді.
- Для чистоти метрик із розрахунку покриття виключено DTO, конфігурації, сутності, енуми, винятки та сідери (`sonar.coverage.exclusions`).

#### 2. Локальний перегляд покриття тестами
Щоб запустити тести та згенерувати локальний HTML-звіт без відправки на хмару:
```bash
./gradlew test jacocoTestReport
```
Після виконання відкрийте у браузері файл `build/reports/jacoco/test/html/index.html`.

#### 3. Повністю автоматичний CI (GitHub Actions)
Вам не потрібно запускати Sonar або тримати токени локально, він запускається автоматично при PR.
