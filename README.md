# UniBook Publisher

Модульна платформа для автоматизації видавничих процесів: супровід повного життєвого циклу рукописів від первинного подання автором до по-главної редактури, рецензування, дизайну обкладинок, фінансового контрактування та нарахування роялті.

## 2. Архітектура системи (Spring Modulith)

Проєкт спроєктовано за парадигмою модульного моноліту на базі Spring Modulith. Домени інкапсульовані та взаємодіють між собою через асинхронні транзакційні доменні події з використанням `@ApplicationModuleListener`, що гарантує надійність доставки, ізоляцію збоїв та усуває пряму циклічну зв'язаність між модулями.

```
src/main/java/com/unibook/publisher/
├── production/        # Життєвий цикл рукописів, розділи, версіонування, дизайн, рецензування, diff-порівняння
├── finance/           # Видавничі контракти, стратегії роялті, нарахування виплат, фіксація продажів
├── identity/          # Користувачі, ролі, профілі, безпечна автентифікація та авторизація
├── communication/     # Сповіщення користувачів, асинхронна реакція на події життєвого циклу
└── common/            # Спільне доменне ядро: події, енуми, ієрархія винятків, логування, GlobalExceptionHandler
```

### 2.1. Опис модулів

- **production**: Відповідає за процес підготовки книги до друку: приймання рукописів, редакторську модерацію головним редактором, розбиття на розділи, завантаження ревізій із текстовим контентом, построкове diff-порівняння версій, коментування фрагментів тексту з перевіркою цитат, пропозиції та автозаміну правок через треди, підготовку варіантів обкладинок та фіналізацію перед публікацією.
- **finance**: Керує договірними відносинами з авторами: формування контрактів, зміна ставок авторського роялті, протоколювання фінансового аудиту, симуляція та розрахунок винагороди на основі гнучких стратегій нарахування роялті (фіксована ставка, прогресивна шкала від обсягу, покриття авансу).
- **identity**: Забезпечує управління обліковими записами, профілями авторів та співробітників, автентифікацію з використанням BCrypt-хешування паролів та розподіл прав доступу на базі ролей (`AUTHOR`, `EDITOR`, `CHIEF_EDITOR`, `DESIGNER`, `ADMIN`).
- **communication**: Централізований сервіс доставлення сповіщень. Асинхронно слухає події інших модулів через `@ApplicationModuleListener` та надсилає користувачам повідомлення щодо зміни статусів рукописів, призначень у команду, нових коментарів, ревізій чи підтвердження контрактів.
- **common**: Спільний фундаментальний модуль, який містить:
  - Доменні події (`common.event`): незмінні записи, що передаються між модулями через шину подій Spring.
  - Загальні переліки (`common.enums`): статуси контрактів, типи обговорень, стратегії роялті, системні ролі.
  - Доменні винятки (`common.exception`): структурована ієрархія помилок на чолі з абстрактним `DomainException`.
  - Підсистему логування (`common.logging`): уніфікований інтерфейс `AppLogger` з реалізацією `SystemOutAppLogger` та конфігурацією `LoggingConfig` для структурованого логування доменних подій та операцій.
  - Централізований обробник помилок (`GlobalExceptionHandler`), що трансформує винятки у стандартні HTTP-відповіді RFC 9457.

## 3. Формальна модель переходів станів

Переходи між станами доменних сутностей строго формалізовані та інкапсульовані в енумах через методи `canTransitionTo(next)` та `allowedTransitions()`. Будь-яка спроба виконати недозволений перехід блокується на рівні доменної моделі та викликає виняток `InvalidStateTransitionException`.

### 3.1. Життєвий цикл рукопису (ManuscriptStatus)

Стани рукопису відображають послідовні етапи підготовки книги:
- `SUBMITTED`: Рукопис надіслано автором; очікує первинної редакційної оцінки.
- `POSTPONED`: Розгляд відкладено редактором; рукопис повернено автору на доопрацювання з обов'язковим коментарем.
- `IN_PROGRESS`: Рукопис схвалено редактором; ведеться по-главна редактура, завантаження ревізій та обговорення правок.
- `TEXT_APPROVED`: Роботу редактора над текстом успішно завершено (усі зауваження та треди закрито).
- `IN_DESIGN`: Текст передано дизайнеру; триває розробка та затвердження обкладинки.
- `PUBLISHED`: Книгу опубліковано у видавництві (наявна затверджена обкладинка). Фінальний успішний стан.
- `REJECTED`: Рукопис відхилено редактором із зазначенням причини. Термінальний стан.

#### Матриця переходів станів рукопису

| Поточний стан     | SUBMITTED | POSTPONED | IN_PROGRESS | TEXT_APPROVED | IN_DESIGN | PUBLISHED | REJECTED  |
|:------------------|:---------:|:---------:|:-----------:|:-------------:|:---------:|:---------:|:---------:|
| **SUBMITTED**     |     -     | ДОЗВОЛЕНО |  ДОЗВОЛЕНО  |       -       |     -     |     -     | ДОЗВОЛЕНО |
| **POSTPONED**     |     -     |     -     |  ДОЗВОЛЕНО  |       -       |     -     |     -     | ДОЗВОЛЕНО |
| **IN_PROGRESS**   |     -     |     -     |      -      |   ДОЗВОЛЕНО   |     -     |     -     |     -     |
| **TEXT_APPROVED** |     -     |     -     |      -      |       -       | ДОЗВОЛЕНО |     -     |     -     |
| **IN_DESIGN**     |     -     |     -     |      -      |       -       |     -     | ДОЗВОЛЕНО |     -     |
| **PUBLISHED**     |     -     |     -     |      -      |       -       |     -     |     -     |     -     |
| **REJECTED**      |     -     |     -     |      -      |       -       |     -     |     -     |     -     |

#### Списки дозволених переходів:
- `SUBMITTED` ➔ `POSTPONED`, `IN_PROGRESS`, `REJECTED`
- `POSTPONED` ➔ `IN_PROGRESS`, `REJECTED`
- `IN_PROGRESS` ➔ `TEXT_APPROVED`
- `TEXT_APPROVED` ➔ `IN_DESIGN`
- `IN_DESIGN` ➔ `PUBLISHED`
- `PUBLISHED` ➔ переходи відсутні (фінальний стан)
- `REJECTED` ➔ переходи відсутні (термінальний стан)

---

### 3.2. Життєвий цикл видавничого контракту (ContractStatus)

- `DRAFT`: Проєкт контракту створено; умови узгоджуються з автором.
- `ACTIVE`: Контракт підтверджено; діє офіційна ставка роялті, дозволено фіксацію продажів та виплати.
- `TERMINATED`: Договірні відносини розірвано або термін дії вичерпано. Термінальний стан.

#### Матриця переходів станів контракту

| Поточний стан  | DRAFT |  ACTIVE   | TERMINATED |
|:---------------|:-----:|:---------:|:----------:|
| **DRAFT**      |   -   | ДОЗВОЛЕНО | ДОЗВОЛЕНО  |
| **ACTIVE**     |   -   |     -     | ДОЗВОЛЕНО  |
| **TERMINATED** |   -   |     -     |     -      |

#### Списки дозволених переходів:
- `DRAFT` ➔ `ACTIVE`, `TERMINATED`
- `ACTIVE` ➔ `TERMINATED`
- `TERMINATED` ➔ переходи відсутні

---

### 3.3. Життєвий цикл обговорень і коментарів (ThreadStatus)

- `OPEN`: Тред активний; триває обговорення фрагмента тексту, обкладинки чи загальних питань.
- `RESOLVED`: Зауваження враховано, питання узгоджено.

#### Матриця переходів станів обговорення

| Поточний стан |   OPEN    | RESOLVED  |
|:--------------|:---------:|:---------:|
| **OPEN**      |     -     | ДОЗВОЛЕНО |
| **RESOLVED**  | ДОЗВОЛЕНО |     -     |

- Перехід `OPEN` ➔ `RESOLVED`: закриття обговорення після внесення правок.
- Перехід `RESOLVED` ➔ `OPEN`: повторне відкриття треду у разі виникнення нових зауважень.

---

### 3.4. Статуси пропозицій заміни тексту (SuggestionStatus)

- `PENDING`: Редактор запропонував альтернативний варіант фрагмента; очікує рішення автора.
- `ACCEPTED`: Пропозицію прийнято; запропонований текст автоматично застосовується до розділу.
- `REJECTED`: Пропозицію відхилено; оригінальний текст розділу залишається без змін.

#### Матриця переходів станів пропозиції

| Поточний стан | PENDING | ACCEPTED  | REJECTED  |
|:--------------|:-------:|:---------:|:---------:|
| **PENDING**   |    -    | ДОЗВОЛЕНО | ДОЗВОЛЕНО |
| **ACCEPTED**  |    -    |     -     |     -     |
| **REJECTED**  |    -    |     -     |     -     |

- `PENDING` ➔ `ACCEPTED`, `REJECTED`
- `ACCEPTED`, `REJECTED` ➔ термінальні стани

## 4. Опис бізнес-правил платформи

### 4.1. Модуль Production

1. **Правило валідації переходів станів**: Будь-яка зміна статусу рукопису повинна відповідати методу `ManuscriptStatus.canTransitionTo()`. При спробі не валідного переходу генерується `InvalidStateTransitionException` (HTTP 422) із повним контекстом допустимих станів.
2. **Правило модерації та обов'язкового обґрунтування**: 
   - Модераційні рішення щодо рукопису приймаються виключно головним редактором (`UserRole.CHIEF_EDITOR`, перевірка заголовка `X-User-Role`). При спробі виконати дію користувачем з іншою роллю викидається `ForbiddenActionException` (HTTP 403).
   - Схвалення рукопису (`approveManuscript`) переводить твір зі статусу `SUBMITTED` або `POSTPONED` у статус `IN_PROGRESS` та генерує подію `ManuscriptApprovedEvent` і призначення редактора `WorkerAssignedEvent`.
   - Відхилення рукопису (`rejectManuscript`) вимагає непорожньої причини (`reason`). Переводить рукопис у статус `REJECTED` та генерує `ManuscriptRejectedEvent`.
   - Відкладення рукопису (`postponeManuscript`) вимагає обов'язкового коментаря редактора (`comment`). Переводить рукопис у статус `POSTPONED` та генерує `ManuscriptPostponedEvent`.
3. **Правило фіналізації тексту**: Завершення редакторської роботи над текстом (`finalizeText`) дозволено виключно за умови, що всі треди обговорень для всіх розділів рукопису мають статус `RESOLVED`. Якщо існує хоча б один відкритий тред (`ThreadStatus.OPEN`) або нерозглянута пропозиція правки, дія блокується викиданням `UnresolvedThreadsException` (HTTP 422).
4. **Правило обов'язкової наявності обкладинки для публікації**: Переведення книги зі статусу `IN_DESIGN` у `PUBLISHED` (`publishBook`) дозволено тільки у випадку, коли в системі зареєстровано хоча б одну затверджену версію обкладинки для цього рукопису. Якщо затвердженої обкладинки немає, викидається `MissingCoverException` (HTTP 422).
5. **Правило унікальності активної обкладинки**: Одночасно затвердженою (`isApproved == true`) для рукопису може бути лише одна версія обкладинки. Затвердження нової версії автоматично деактивує статус попередньої.
6. **Правило валідації цитування тексту**: Для тредів обговорень, що створюються з прив'язкою до ревізії розділу (`targetRevisionId`), здійснюється сувора перевірка:
   - Текст цільової ревізії не може бути порожнім або відсутнім (інакше `EmptyRevisionTextException`, HTTP 422).
   - Символьні позиції повинні задовольняти умовам: `0 <= positionFrom < positionTo <= textContent.length()` (інакше `InvalidQuotePositionException`, HTTP 422).
   - Текст підрядка за вказаними координатами повинен точно збігатися з переданою цитатою `quotedText` (інакше `InvalidQuoteException`, HTTP 422).
7. **Правило операцій над пропозиціями та автоматичної заміни тексту**: Операції прийняття (`acceptSuggestion`) та відхилення (`rejectSuggestion`) правок можуть застосовуватися виключно до тредів, створених як пропозиції заміни тексту (`isSuggestion == true`). При спробі застосувати їх до звичайного обговорення викидається `ThreadNotASuggestionException` (HTTP 422). Прийняття пропозиції автоматично замінює фрагмент тексту ревізії у діапазоні `[positionFrom, positionTo)` на `suggestedText`, зберігає оновлену ревізію та переводить тред у статус `RESOLVED` зі статусом пропозиції `ACCEPTED`.
8. **Правило порівняння ревізій розділу (Diff Engine)**: Платформа підтримує побудову построкової різниці (diff) між будь-якими двома ревізіями розділу (`GET /api/v1/chapters/{chapterId}/diff?fromRevisionId=...&toRevisionId=...`). Порівняння повертає структуровану відповідь `DiffResponse`, яка містить перелік рядків із їхнім статусом `DiffStatus` (`EQUAL`, `INSERTED`, `DELETED`) та 1-based номерами у вихідній (`oldLineIndex`) і цільовій (`newLineIndex`) версіях.
9. **Правило унікальності призначення співробітника**: Один і той самий користувач не може бути призначений двічі на одну й ту саму роль (`UserRole`) для одного рукопису. Повторна спроба блокується винятком `StaffAlreadyAssignedException` (HTTP 409).
10. **Правило обов'язкового аудиту дій**: Усі редакторські дії (зміна станів, відкладення, схвалення, фіналізація, призначення персоналу) фіксуються в журналі аудиту `ManuscriptAuditLog` із зазначенням автора дії, ідентифікатора рукопису, типу операції та мітки часу.

### 4.2. Модуль Finance

1. **Правило активності контракту для фінансових розрахунків**: Операції фіксації продажу книг та нарахування авторської винагороди (роялті) дозволені виключно за наявності контракту у статусі `ContractStatus.ACTIVE`. Спроба нарахувати кошти за неактивним або розірваним контрактом викликає виняток `ContractNotActiveException` (HTTP 422).
2. **Правило процентної ставки роялті**: Ставка авторського роялті повинна бути строго додатною та не перевищувати 100% (`0 < royaltyPercent <= 100`).
3. **Правило стратегій розрахунку роялті (RoyaltyStrategy)**: Розрахунок винагороди автора та симуляція виплат (`simulatePayout`) підтримують вибір алгоритму згідно з патерном Strategy (`RoyaltyStrategyType`):
   - `FLAT_RATE` (Фіксована ставка): роялті розраховується як прямий відсоток від суми продажів: $\text{salesAmount} \times \text{royaltyPercent} / 100$.
   - `TIERED_VOLUME` (Прогресивна шкала): процентна ставка змінюється динамічно залежно від обсягу продажів (до 1 000 грн — 5%, від 1 000 до 5 000 грн — 7%, понад 5 000 грн — 10%).
   - `ADVANCE_RECOUPMENT` (Покриття авансу): нараховане за базовою ставкою роялті спочатку спрямовується на погашення раніше виданого автору авансу (`advancePayment`), і лише залишок понад суму авансу нараховується до виплати ($\max(0, \text{royalty} - \text{advancePayment})$).
   - При спробі використання непідтримуваної або невідомої стратегії генерується виняток `UnsupportedRoyaltyStrategyException` (HTTP 422).
4. **Правило аудиту фінансових параметрів**: Кожне оновлення ставки роялті фіксується у фінансовому журналі аудиту `FinanceAuditLog` із фіксацією попереднього та нового відсотка і супроводжується публікацією події `ContractRoyaltyUpdatedEvent`.
5. **Правило незворотності розірвання**: Переведення контракту у статус `TERMINATED` є остаточним; відновлення розірваного контракту заборонено.

### 4.3. Модуль Identity

1. **Правило унікальності адреси електронної пошти**: Реєстрація нового автора (`register`) або створення облікового запису співробітника адміністратором (`createStaff`) з електронною поштою, яка вже зареєстрована в системі (без урахування регістру), заборонена. Викидається виняток `EmailAlreadyExistsException` (HTTP 409).
2. **Правило захищеної автентифікації**: У разі невірного пароля або відсутності користувача з вказаною поштою сервіс повертає уніфікований виняток `InvalidCredentialsException` (HTTP 401) без розкриття інформації про те, яка саме частина облікових даних була невірною.
3. **Правило криптографічного захисту паролів**: Паролі користувачів обов'язково хешуються алгоритмом BCrypt із використанням випадкової солі перед збереженням у базі даних. Збереження паролів у відкритому вигляді суворо заборонено.
4. **Правило розподілу обов'язків**: Права доступу до ресурсів розділені за ролями:
   - `AUTHOR`: Подання власних рукописів, перегляд коментарів, відповіді в тредах, прийняття або відхилення пропозицій правок, перегляд власних контрактів та симуляція нарахувань роялті.
   - `EDITOR`: Ведення по-главної редактури, створення ревізій, відкриття тредів із цитатами та пропозиціями заміни тексту, затвердження тексту книги.
   - `CHIEF_EDITOR`: Головний редактор із виключними правами модерації первинних заявок (схвалення, відхилення, відкладення рукописів), призначення дизайнерів та публікації фіналізованих книг.
   - `DESIGNER`: Завантаження та оновлення версій обкладинок книг, обговорення візуальної частини.
   - `ADMIN`: Створення облікових записів співробітників, системний моніторинг.

### 4.4. Модуль Communication

1. **Правило авторизації доступу до сповіщень**: Користувач має право переглядати та відмічати як прочитані (`markAsRead`) виключно ті сповіщення, адресатом яких він є (`recipientId == currentUserId`). Спроба змінити статус чужого сповіщення відхиляється винятком `ForbiddenActionException` (HTTP 403).
2. **Правило ідемпотентності прочитання**: Повторне позначення сповіщення, яке вже має статус `isRead == true`, є ідемпотентним і не призводить до помилок.
3. **Правило асинхронного реагування на події**: Модуль комунікації є виключно реактивним і формує сповіщення на підставі доменних подій, опублікованих іншими модулями системи:
   - `ManuscriptSubmittedEvent` ➔ сповіщення автору про успішну подачу та взяття на модерацію.
   - `ManuscriptApprovedEvent` ➔ сповіщення автору про схвалення твору редактором.
   - `ManuscriptRejectedEvent` ➔ сповіщення автору з обов'язковою причиною відхилення.
   - `ManuscriptPostponedEvent` ➔ сповіщення автору із зауваженнями редактора.
   - `TextFinalizedEvent` ➔ сповіщення про офіційне завершення редактури тексту книги.
   - `ManuscriptPublishedEvent` ➔ сповіщення автору про публікацію книги.
   - `ContractConfirmedEvent` ➔ сповіщення автору про підтвердження умов контракту.
   - `ContractRoyaltyUpdatedEvent` ➔ сповіщення про зміну відсоткової ставки винагороди.
   - `WorkerAssignedEvent` ➔ сповіщення призначеному фахівцю та автору книги про оновлення команди проєкту.
   - `CoverVersionAddedEvent` ➔ сповіщення автору про завантаження дизайнером нового варіанту обкладинки.
   - `RevisionAddedEvent` ➔ сповіщення автору про завантаження нової редагованої версії розділу.
   - `ThreadOpenedEvent` ➔ сповіщення про відкриття нової гілки обговорення із диференціацією типу (розділ, обкладинка чи загальне питання).
   - `ThreadMessageAddedEvent` ➔ сповіщення адресату про нове повідомлення в треді.

## 5. Ієрархія доменних винятків та обробка помилок

Усі винятки бізнес-рівня системи організовані в типізовану ієрархію з єдиним базовим абстрактним класом `DomainException` (`extends RuntimeException`). Винятки згруповані за смисловими пакетами відповідно до характеру помилки та транслюються `GlobalExceptionHandler` у відповідні HTTP-статуси згідно зі специфікацією RFC 9457 (`ProblemDetail`).

│
├── notfound/                                           # HTTP 404 NOT FOUND
│   ├── ResourceNotFoundException.java                  # Базовий клас для відсутніх ресурсів
│   ├── ManuscriptNotFoundException.java
│   ├── ChapterNotFoundException.java

│   ├── UserNotFoundException.java

│
├── state/                                              # HTTP 422 UNPROCESSABLE ENTITY
│   └── InvalidStateTransitionException.java            # Помилка переходу між станами
│
├── business/                                           # HTTP 422 UNPROCESSABLE ENTITY
│   ├── BusinessRuleViolationException.java             # Базовий клас порушення бізнес-правил
│   ├── UnresolvedThreadsException.java                 # Наявність незакритих тредів перед фіналізацією
│   ├── MissingCoverException.java                      # Спроба публікації без затвердженої обкладинки

## 7. Конфігурація та локальний запуск

### 7.1. Змінні оточення

Для зручного локального налаштування параметрів без зміни вихідного коду використовується файл `.env`. У репозиторії надано шаблон `.env.example`, що містить зразок усіх підтримуваних системних змінних.

Для початку роботи скопіюйте шаблон:
```bash
cp .env.example .env
```

> [!NOTE]
> Файл `.env` додано до `.gitignore`, тому локальні налаштування та облікові дані до баз залишаються конфіденційними. Додаток автоматично зчитує змінні з `.env` на старті.

#### Опис груп параметрів:

1. **База даних за замовчуванням (H2 In-Memory)**:
   - `DB_URL`: JDBC URL для вбудованої бази H2 (за замовчуванням `jdbc:h2:mem:unibook_db;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE`).
   - `DB_DRIVER`: драйвер `org.h2.Driver`.
   - `DB_USER` / `DB_PASSWORD`: облікові дані (`sa` / без пароля).
   - `H2_CONSOLE_ENABLED`: активація веб-консолі H2 (`true`).

2. **База даних PostgreSQL (Локальна або спільний сервер команди)**:
   - `DB_HOST`, `DB_PORT`, `DB_NAME`: мережева адреса, порт та назва бази даних (за замовчуванням `localhost:5432/unibook_db`).
   - `DB_USER`, `DB_PASSWORD`: облікові дані користувача PostgreSQL.
   - `DB_URL`: повний JDBC URL (`jdbc:postgresql://${DB_HOST}:${DB_PORT}/${DB_NAME}`).
   - `DB_DRIVER`: драйвер `org.postgresql.Driver`.

3. **JPA та Hibernate**:
   - `JPA_DDL_AUTO`: режим генерації структури БД (`update`, `validate`, `create-drop`).
   - `JPA_SHOW_SQL` / `JPA_FORMAT_SQL`: логування та форматування SQL-запитів у консолі.

4. **S3 Сховище (Garage / MinIO / Cloudflare R2)**:
   - `S3_ENDPOINT`: URL точки доступу до S3 (наприклад, `http://localhost:3900`).
   - `S3_BUCKET`: назва робочого бакета.
   - `S3_ACCESS_KEY` / `S3_SECRET_KEY`: ключі доступу S3 API.

### 7.2. Наслідування конфігурацій (Properties & Profiles)

Конфігурація системи побудована за ієрархічним принципом без дублювання налаштувань:
- **`application.properties` (Базовий файл)**: містить спільні налаштування застосунку, Jackson, безпечні дефолти JPA/Hibernate та фолбеки для H2. Усі інші профілі автоматично наслідують ці параметри.
- **`application-postgres.properties` (Профіль Postgres)**: активується прапорцем `--spring.profiles.active=postgres`. Він перевизначає виключно параметри джерела даних (`spring.datasource.*`) під PostgreSQL та вимикає консоль H2, автоматично успадковуючи всі JPA-налаштування з базового файлу.

> [!TIP]
> **Перемикання між H2 та PostgreSQL можна виконати двома зручними шляхами:**
> 1. **Через `.env`**: закоментувати блок H2 та розкоментувати блок PostgreSQL у власному файлі `.env`.
> 2. **Через профіль Spring**: запустити додаток із параметром `--spring.profiles.active=postgres`.

git clone https://github.com/DaniloBez/UniBook-Publisher.git

### 7.5. Аналіз якості коду та тестового покриття (SonarCloud & JaCoCo)

Для забезпечення високої надійності, безпеки та чистоти коду в проєкті інтегровано зв'язку **JaCoCo + SonarCloud**.

#### 1. Як це працює
- **JaCoCo**: під час запуску тестів збирає статистику виконання рядків і гілок коду та генерує XML-звіт (`build/reports/jacoco/test/jacocoTestReport.xml`) і локальний HTML-звіт (`build/reports/jacoco/test/html/index.html`).
- **SonarCloud**: отримує вихідний код і JaCoCo XML-звіт, аналізує вразливості, баги, code smells та відображає підсумковий відсоток покриття на Quality Gate дашборді.
- Для чистоти метрик із розрахунку покриття виключено DTO, конфігурації, сутності, енуми, винятки та сідери (`sonar.coverage.exclusions`).

#### 2. Локальний перегляд покриття тестами
Щоб запустити тести та згенерувати локальний HTML-звіт без відправки на хмару:
```bash
./gradlew test jacocoTestReport
```
Після виконання відкрийте у браузері файл `build/reports/jacoco/test/html/index.html`.

#### 3. Повністю автоматичний CI (GitHub Actions)
Вам не потрібно запускати Sonar або тримати токени локально, він запускається автоматично при PR.
